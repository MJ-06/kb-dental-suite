# Review of saas/multi-clinic (31 Oct 2026)

Scope: read STATUS.md, docs, migrations 0001-0022, auth, /exec layer, app.ts, storage, secrets, Drive client, test list. Nothing was run (no tests, no server) and no files were edited. The design artifact was not read (it opens only through the Docs connector). The in-progress work of the four other threads (migrations 0020-0022, uncommitted edits) was read only at the schema level.

The core is good: forced RLS with fail-closed tenant setting, a non-owner app role, append-only audit/consents/receipts, hashed session tokens, lockout, per-request CSP. The gaps below are mostly what happens when it leaves the laptop.

## High

1. **No deployment or backup artefacts exist.** The repo has no nginx config, systemd/Windows service definition, `pg_dump`/restore script, restore test or monitoring. For a clinical record this is the biggest gap. Fix: add `ops/` with an nginx site (TLS, gzip, `client_max_body_size`, proxy headers), a service unit, a nightly `pg_dump` + WAL archive to off-site storage, and a documented, tested restore (run it once on a clean machine).
2. **Per-clinic DB move is promised but not wired.** `clinics.database_url` is read by nothing; `server.ts` creates one pool. Login, `session_resume`, `clinic_today` and `sessions` all assume one central DB. Moving a clinic out needs a router (clinic code -> pool), a central directory DB for login/sessions, and per-clinic migrations. Fix: decide the model now (central directory + per-clinic pools), or drop the column and say "one shared DB; export per clinic by `pg_dump` with a clinic filter". Do not leave the column implying support.
3. **Role names are used as permissions in forms.** Migration 0021 stores `fill_roles`/`view_roles` as role *names* (`{admin,doctor}`), but 0020 lets clinics rename and create roles. After a rename, or in a clinic with a "dentist" role, the form rules silently match nobody or the wrong people. Fix: gate forms by permission (`clinical:write`) or reference `roles.id`, never a name. Also nothing yet uses `src/forms` (directory absent), so this is still cheap to change.
4. **No protection against lost updates.** Every table has a `version` column, but no legacy action checks it (no hits in finance or patients). Two desks saving the same patient, plan or master list: last save wins. "Each list saves whole" makes this worse (one desk's list erases another's). Fix: send `version` from the screen and `WHERE version = $n`; at minimum on masters lists, treatment plans, and patient edits.
5. **Mobile data: nothing is compressed or cached.** `index.html` is 2.7 MB served uncompressed with `Cache-Control: no-store` on every response except `/vendor/`. No gzip/brotli in the app. Babel runs in the browser on the chatbot page. Fix: nginx gzip/brotli (about 2.7 MB -> under 600 KB), content-hash the page and let it cache with revalidation, precompile JSX, split the monolith when practical. Uploads of 25 MB as base64 over `/exec` (about 33 MB) need resumable or direct-to-storage upload (signed URL), plus a client-side image downscale for phone photos.

## Medium

6. **Rate limits are per IP; mobile carriers share IPs (CGNAT).** Many staff on phone data can share one address, so the 10/min login limit and 900/min `/exec` limit can lock real users out together, and one noisy device can throttle a clinic. Fix: key limits on session (after sign-in) and on clinic code + username for login, keep IP as a coarse backstop.
7. **Account lockout is a denial-of-service lever.** Anyone knowing a clinic code and username can lock that account every 15 minutes with 5 bad guesses. Acceptable for ten clinics if you know it; mitigate with per-IP counters before the lock and an admin "unlock" action.
8. **Session model is thin for phones.** 12 h desk TTL, no device list, no "sign out everywhere", no forced sign-out on password reset or role change (role change applies per request, but a deactivated user's sessions only die by the `active` check). The phone session (0021) is a good start; add revoke-all-on-password-change and an admin session list.
9. **Cross-tenant tests are hand-picked, not exhaustive.** `isolation.test.ts` checks patients and a few DB cases. Nothing asserts that *every* table with `clinic_id` has forced RLS and the policy, and nothing proves it after each new migration (0020-0022 add four tables this week). Fix: one test that queries `pg_class`/`pg_policy`, fails on any public table that has `clinic_id` and lacks forced RLS, plus a generic "clinic B sees zero rows of every table clinic A filled" test. Also `sessions` is RLS-enabled but not forced and `kb_app` can still read/delete its own clinic's rows; it is fine, but note `session_resume` and `phone_session_expire` are SECURITY DEFINER with a fixed `search_path`; keep that pattern in code review.
10. **Secrets and credentials.** `KB_SECRETS_KEY` is one key for all clinics' Drive/S3 credentials, with no rotation path (`v1` prefix helps). Losing it means re-entering credentials; leaking it plus a DB backup exposes every clinic. Fix: key id in the sealed string and a rotate script; store the key outside the DB backup's reach.
11. **Migrations 0001-0006 were edited in place and are not frozen.** Fine before first deployment, but the migrator refuses changed files after apply, so freeze them now and note the date in STATUS.md.
12. **One transaction per request, 10-connection pool, 15 s statement timeout.** Fine for about 10 clinics. The risks are the `/exec` `batch` (up to 25 parallel transactions from one request can drain the pool) and report/export queries; give reports a separate small pool or timeout, and cap batch concurrency to 4.
13. **Audit log grows forever and copies full rows** (`before_row`/`after_row` jsonb for every write, including the bulky `values` of form submissions). Plan partitioning or archival by month, and keep documents' bytes out (they are already files).
14. **Documents.** Server-folder storage is a single point of loss until the S3/Drive thread lands; the checksum column helps. Verify that deleting a document in a clinic never touches another clinic's key (key = clinic/doc uuid, good), that the Drive "full drive scope" is really needed (it can see the whole Drive of the connected account), and add antivirus or at least a type allow-list on upload (already partial via `safeType`).

## Low

15. Hard-coded K.B. Dental text (letterhead, signature lines, chatbot name) makes the product single-tenant visually.
16. `jspdf 2.5.1` has advisories; schedule the upgrade.
17. `GET /exec` writes rely on SameSite=Strict only; acceptable now, move writes to POST-only when screens allow.
18. No phone layout (known). If clinics use phones for forms and the diary, this is a product item, not an afterthought; the form-entry thread should own a responsive shell rather than adapting the 2.7 MB desk app.
19. The repo carries a stray file named `nul` at the root (breaks `rg` and some Windows tools) and two nested copies (`kb-dental-suite/`, `server/`) of the old code; delete after the migration lands.
20. Only one `STATUS.md` claim to recheck: "195 pass" on the branch tip; I did not run it.

## Testing gaps

- No end-to-end browser tests are committed (flows were clicked by hand, results live in the artifact).
- No test for role/permission *changes* mid-session, concurrent saves, or large uploads over slow links.
- No restore drill, no migration-on-a-copy-of-real-data check (the real Sheets are not yet imported).

## Questions for Diya

1. Is the per-clinic database an actual requirement at ten clinics, or a "keep the door open"? The answer decides item 2 (build a router now, or drop the column).
2. Will staff use phones for the diary and forms, or only for entry on the go? That sets how far item 5 goes.
3. Where will this be hosted (your own machine, a VPS, a managed Postgres)? Items 1, 5 and 12 change with that.
4. Who restores a backup at 9 pm when something goes wrong, and how long may the clinic be without records?
